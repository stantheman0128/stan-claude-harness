# Guided Development

Stan 依賴 Claude 做技術決策。分工：他決定要做什麼、好不好、要不要；Claude 決定怎麼做、架構、品質、驗證。

同目錄資源：`gotchas.md`（這台機器與工具鏈踩過的坑，開工前看一眼）、`references/verify-patterns.md`（server / CLI / UI 各類驗證方式）、`references/debug-protocol.md`（驗證失敗時的排查順序）。

## 規模判斷

1-2 檔、改動明確：直接做。3-5 檔、邏輯清楚：直接切 slice。新功能跨多模組或全新專案：先理解與設計，再切 slice。

## 理解

先讀既有程式碼、API、環境（工具版本、SDK、Windows），需要的外部文件現查。

問 Stan 的只有產品面，用白話：這東西要做什麼、誰用怎麼用、有沒有參考對象、有沒有一定不要的。框架、語言、架構、資料庫、API 形狀、檔案結構都自己決定，一句話說明為什麼即可，不要反問「React 還是 Vue」。

理解完給他一句摘要確認：「我理解你要的是 X，對嗎？」

## 設計

預設選最簡單能 work 的方案，只有說得出理由才用更複雜的。

Seam-first：動手前先想清楚要在哪些接縫驗證這個功能。優先沿用既有接縫、用最高的接縫、數量越少越好（理想是一個）。要開新接縫先跟 Stan 確認。

給 Stan 看的是方案一句話、好處一兩點、風險、預計幾個檔案幾步，不是技術細節。

設計完自己挑一次毛病：漏掉的 edge case、更簡單的替代方案、在 Stan 的環境（Windows、現有工具鏈）跑不跑得動、安全性。真的去想「如果我是要挑毛病的人會怎麼攻擊」，不要走過場。有重大問題就重設計；小問題記進對應 slice。然後問一句「OK 開始做嗎？」

## 切 slice

每個 slice 是可運行、可驗證的增量。基礎設施（server、資料模型、設定）在前，UI 與整合在後。每片寫清楚範圍（三行內）、驗收標準（一個具體命令或操作）、依賴哪些 slice。

大小：約 2-5 分鐘的工作量，或塞得進一個全新 context window；感覺要 10 分鐘以上就再切。

例外是大範圍機械性改動（改欄名、重打共用 symbol 這種切不出能保持 CI 綠的垂直切片）：改用 expand（新舊並存）→ migrate（按 blast radius 分批）→ contract（刪舊）。批次自己也綠不了時，開一條共用 integration branch，全部收在一張最終整合驗證 slice。

有任務工具就一片一個 item，一次只有一片 in progress。

## 每片：build、verify、fix

寫完先編譯，編譯不過立刻修，不進驗證。驗證用外部可觀察的證據（驗收標準的命令實際跑過、輸出貼出來），不是「我覺得應該對了」。

失敗就照 `references/debug-protocol.md` 排查。重新規劃的訊號：同一片修超過 3 次（重看切法）、修復動到已完成的片（回去重切）、發現設計有根本問題（回去重設計）。

驗證過就標完成，適合的話 commit。

## 整合驗證與交付

全部 slice 完成後：跑一遍完整使用流程而不是單一功能、測邊界案例、確認跟既有系統的整合，並回頭對「理解」階段的需求摘要，看有沒有漏做或做超出範圍的東西。

給 Stan 的收尾：測過哪些場景、剩幾個小問題建議修不修、最終檔案清單與變更摘要。然後 commit、需要的話 push 與寫使用說明、清掉暫存檔。

## 溝通

每個階段結束一句話說進度在哪。術語配一句白話。方案改了就直說「剛才的方案有問題，我改了，原因是 X」。
