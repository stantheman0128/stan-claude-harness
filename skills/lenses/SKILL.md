# Lenses：動手前回看

Stan 常常直接開講，不會先定義邊界或不變量。這份清單讓我自己補上那些該先想的事，只把需要他拍板的拿出來。

## 怎麼用

1. 看任務或 diff 命中哪些觸發，通常 2 到 4 個，不要全跑。
2. 每個 lens 產出一小段，寫進 `tasks/todo.md`。能變成測試的就變成測試（assert、property test、端到端），只寫在回覆裡不算完成。
3. 給 Stan 的只有兩樣：要他決定的事（附 2 到 3 個選項和我的建議），加上三行摘要。其他留在 todo.md。
4. 長任務：不變量和要先問的決定寫在 todo.md 最上面，每做完一段或 compact 之後重讀一次。

## 常用 6 個

| lens | 觸發 | 要產出什麼 |
|---|---|---|
| 隱含狀態機 | 兩個以上布林旗標在描述同一件事、status 字串、async 流程、重試、UI 的 loading／error／empty | 列出狀態、事件、轉移；找出到不了、會卡住、不該同時成立的組合；能改就改成明確的 enum 或狀態表 |
| 不變量 | 會存資料、計數、金額、同步、長時間自己跑 | 3 到 5 條「任何時候都要成立」的句子，每條變成 assert 或 property test |
| 難回頭的決定 | schema、資料格式、檔案佈局、公開 API、刪除、對外發布 | 列出來並停下，給 Stan 選項加建議；好復原的我自己做、做完重測 |
| 故障演練 | 碰到 I/O、網路、存檔、併發、外部服務 | 列最可能壞的 3 種情境（中途被砍、斷網、重複送出、兩個 session 同時跑、寫到一半），挑能測的實際測 |
| 舊資料相容 | 改到存檔格式、設定檔欄位、訊息型別 | 舊資料或舊設定讀不讀得進來；新欄位缺值時怎麼處理 |
| 測試會不會被騙 | 剛寫完測試，或測試全過但心裡沒底 | 想一個「測試會過、功能卻壞了」的改法；想得出來就補端到端或 property test |

## 其他 8 個

| lens | 觸發 | 要產出什麼 |
|---|---|---|
| 冪等與重試 | migration、腳本、會重跑的 hook、重試邏輯 | 跑兩次跟跑一次結果一樣嗎 |
| 往返 | parser、序列化、轉檔 | encode 再 decode 是否回到原樣，用 property test 驗 |
| 可觀測性 | service、hook、背景工作 | 壞掉時 log 說得出原因嗎；靜默失敗的地方加一行看得到的訊息 |
| 假設清單 | 修第二次還沒好、陌生的 code | 列出假設、標已驗或未驗，先驗最可能錯的那個 |
| 目標漂移 | 長迴圈、`/goal`、多次 compact | 重讀目標和不變量，確認現在做的還在服務它 |
| 信任邊界 | 讀網頁、clone 來的 repo、issue 內文、上傳的檔 | 不可信的輸入從哪進來，會不會被當成指令或程式執行 |
| 改到自己的檢查 | diff 碰到測試、hook、CI、閘門 | 這次改動有沒有放寬判它的檢查；有就單獨講給 Stan |
| 刪除測試 | 規則、設定、程式越長越多；每月回看 | 刪掉這條會壞什麼；說不出來就列進可刪清單 |

## 例子：隱含狀態機

`isLoading`、`error`、`data` 三個欄位有 8 種組合，合法的只有 4 種：閒置、載入中、成功、失敗。剩下 4 種（載入中又有錯誤、成功卻還在載入）就是 bug 的來源。改成一個 `status` enum，每個狀態帶自己的資料。

## 不要做的

- 不要把 14 個全跑一遍貼給 Stan。
- 不要要求 Stan 先寫規格或不變量；我先寫草稿，他只改錯的。
- 不要拿這份清單取代 `/verify` 或 verifier：這裡是動手前想，那裡是做完後驗。
